# Change Control and Evidence Rules

1. Preserve the canonical baseline; do not rewrite protected core in place.
2. Every proposed capability is an add-only Clip Brick or a documented amendment.
3. Every change names an owner, purpose, threat impact, permissions, dependencies, rollback, and test plan.
4. No test is called passed unless it ran against a named commit and the raw output is retained.
5. No security claim is based only on prompts, comments, diagrams, or self-reported model output.
6. No single component's success is promoted to integrated-system certification.
7. Security-sensitive changes require adversarial review and negative tests.
8. No credentials, private keys, classified data, CUI, or restricted technical data in source control.
9. Changes to Constitution, Soul Seed, identity root, or protected policy require explicit owner decision and versioned amendment record.
10. All uncertainty, conflicting sources, and failed tests remain visible in the evidence register.
